## 2. PRODUCT VARIANTS AND DATABASE DESIGN

Create a clean, normalized product catalogue.

Each product should have:
- Unique ID.
- Canonical product name.
- Slug.
- Main category.
- Subcategory.
- Description.
- Common names and regional names.
- Scientific name where useful and verified.
- Default unit of measurement.
- Suitable product image.
- Seasonal availability information where reliable.
- Storage information where useful.
- Active or inactive status.

Each variety should have:
- Parent product ID.
- Variety name.
- Region or origin where verified.
- Relevant attributes such as colour, grade, size, or type.

Examples:
- Mango → Badami.
- Mango → Alphonso.
- Mango → Raspuri.
- Rice → Sona Masuri.
- Rice → Basmati.
- Chilli → Byadagi.
- Banana → Nanjangud Rasabale.

Do not create a separate unrelated product for every spelling variation. Use canonical names and aliases to avoid duplicate search results.

Supplier-specific information must be stored in supplier_listings, not the canonical products table.

Each supplier listing should include:
- Supplier business.
- Product and optional variety.
- Price.
- Currency.
- Unit.
- Available quantity.
- Minimum order quantity.
- Optional maximum order quantity.
- Quality grade.
- Harvest or production date if applicable.
- Available-from date.
- Delivery area.
- Delivery fee.
- Listing status.
- Product images.
- Updated timestamp.

Do not assign made-up live prices or inventory to canonical products.

If demo prices are used, mark them as sample data and keep them separate from live supplier listings.
